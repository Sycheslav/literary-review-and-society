# English extraction API

`npm run knowledge:en:build` reads the current `content/retellings/registry.json` and builds `knowledge/en/snapshot.json` atomically. `npm run build` and `npm run dev` invoke it after the existing knowledge build. Python 3.10+ and `jsonschema` with Draft 2020-12 support are required at build time (`requirements-en-build.txt` pins the dependencies; the proposed Dockerfile installs them); Next reads the generated snapshot and does not invoke Python at request time. The registry is the authority: only `published_catalog` records are expected, and `attached` IDs resolve to their published `curation.attached_to`. A current, explicitly non-accepted `revise` decision with the documented review fields and a `revision_requested` assignment remains unprocessed. Unsupported or incomplete decisions fail the build. The existing Russian routes are unchanged.

`GET /literature/api/v1/extractions?scope=all&fields=findings,author_conclusions` or `POST` JSON `{"scope":"all","fields":["findings","author_conclusions"]}`. Alternatively specify `ids` (GET comma-separated; POST array). Choose exactly one base selection: `scope=all`, an ID list, or `kind`/`type`. `kind` and `type` are aliases and may also be combined with `scope` or `ids` as a filter. Filters combine with any base selection: `topic`, `concept_question` (stable H IDs), minimum 0–4 thresholds `min_relevance` (R), `min_evidence_strength` (E), `min_reproducibility` (P), `min_transferability` (T), and a 0–100 `min_priority` threshold. All supplied filters must match. Unknown topics/questions are errors. Missing, null, or ambiguous score values do not match a minimum threshold. Coverage retains the pre-filter candidate IDs and lists `filtered_out_ids` separately. R/E/P/T are the current package-level scores; per-question concept links are selected by `concept_question`. Priority uses the stored `priority_hypothesis` score; missing values do not match. Publication status and bibliometric filters are unavailable because the accepted package and current catalog do not yet expose those values.

To retrieve answer records, explicitly include `answers` and select Q-IDs, for example `GET /literature/api/v1/extractions?scope=all&fields=answers&question_ids=Q23,Q51` or POST `{"scope":"all","fields":["answers"],"question_ids":["Q23","Q51"]}`. IDs must be unique and in Q01–Q90. Only `reported` answers are returned by default. Set `include_nonreported=true` to include the other recorded statuses; that explicit option also returns `note_en` and `searched_source_refs` when present. Answer records include `question_id`, `status`, `value`, `origin` when present, and `evidence`; generic question wording is not repeated, and a missing package record is not converted into an absence claim. `include_nonreported` and `question_ids` are rejected unless `answers` is requested. The default fields remain findings and author conclusions, with no `answers` array.

`publication_notice` uses the strict `publication-attribution-notice-v1` contract in `content/analyses/schema/publication-attribution-notice.schema.v1.0.0.json`. The registry-backed builder validates the exact object before copying it unchanged into `data.publication_notice`; it does not interpret the notice as rights approval. When present, the notice is attached to every accepted work record independently of the requested content fields, including each paginated part and each JSONL work line. It is also selectable as a field; for an older accepted snapshot that has no notice, an explicit request returns `publication_notice: null`. Old snapshots without the field and unprocessed works remain valid. Notice and work records contain projected metadata only, never local package or source file paths. The JSONL record digest and HTTP ETag include the notice.

## Post-gate integrator verification

Run these only after the independent export-rights review and separate integrator acceptance are current in the canonical records. They build/publish the snapshot from those records; they are not an acceptance shortcut.

```powershell
npm run build
npm start -- --port 3147
node scripts/en-search.mjs findings --ids arxiv-2410-08948 > en05-cli.json
curl.exe --fail --silent --show-error "http://localhost:3147/literature/api/v1/extractions?ids=arxiv-2410-08948&fields=findings" -o en05-http.json
curl.exe --fail --silent --show-error "http://localhost:3147/literature/api/v1/extractions?ids=arxiv-2410-08948&fields=findings&format=jsonl" -o en05-http.jsonl
node --input-type=module -e "import fs from 'node:fs'; import assert from 'node:assert/strict'; const cli=JSON.parse(fs.readFileSync('en05-cli.json','utf8')); const http=JSON.parse(fs.readFileSync('en05-http.json','utf8')); const [manifestLine,workLine]=fs.readFileSync('en05-http.jsonl','utf8').trimEnd().split('\n'); const manifest=JSON.parse(manifestLine); const jsonlWork=JSON.parse(workLine); assert.equal(cli.snapshot,http.snapshot); assert.equal(manifest.snapshot,http.snapshot); assert.equal(http.works.length,1); assert.deepEqual(cli.findings[0].publication_notice,http.works[0].publication_notice); assert.deepEqual(jsonlWork.publication_notice,http.works[0].publication_notice); console.log(http.snapshot);"
```

The final assertion prints the one snapshot ID shared by CLI JSON, HTTP JSON and the JSONL manifest, and compares the notice from all three outputs. Do not run the build command while EN-05 is still on rights hold or lacks integrator acceptance.

Fields are `findings`, `author_conclusions`, `answers`, `publication_notice`, `prompts`, `concept_links`, and `scores`; omitted fields default to findings and author conclusions. Up to 1000 IDs and 100 KB POST body are accepted. Unknown and duplicate IDs are reported; the response contains snapshot, normalized selection, coverage by ID, and all requested accepted records. It is not a ranked search. Prompts are currently an explicit unavailable status. Optional `limit` (1–100) produces pages with `truncated` and `next_cursor`; send the same selection, filters, fields, and limit with the cursor. For answer requests, the sorted Q-ID selection and `include_nonreported` flag are part of the cursor binding. Each part has zero-based `part_index` and `part_count`; assemble by work ID. A finding exceeding 16,384 UTF-8 JSON bytes is represented by ordered `finding_fragment` records: base64-decode and concatenate their `data`, then parse the UTF-8 JSON. Metadata and coverage accompany pages; selected ancillary fields, including answers, appear only in the first part for that work. `publication_notice` remains attached to every part for attribution. Without `limit`, the complete JSON response is retained.

For a complete JSONL download use `format=jsonl` on GET or POST. JSONL does not use `limit` or cursors. The first line is a manifest with the same snapshot, selection, and coverage, followed by one `type=work` line per accepted work. `records_bytes` and `records_sha256` cover the exact UTF-8 bytes of those work lines including their final LF; verify both before treating the download as complete. The HTTP ETag hashes the complete file including the manifest. The full export is materialized in memory before sending. This is not streaming and has no configurable response-size cap; very large exports can consume substantial memory. An interrupted transfer is incomplete. No original source files or Russian retellings are included. Snapshot and cursor digests detect corruption and mismatch, not authorization; a build and publication must run under integrator control.

`/literature/knowledge/en` is a minimal English entry point. Build output is read-only by the API and is not served directly by the legacy knowledge allowlist. Content-addressed snapshots are retained under `knowledge/en/snapshots/`; the builder adds new immutable archives and atomically replaces the current pointer without pruning older files. Git is the archive store between releases: include each permitted snapshot JSON needed for active cursors in the commit, and let the existing Dockerfile `COPY . .` carry those files from the clean build context. No paid artifact service is required. The nested `.gitignore` and root `.dockerignore` exclude revoked diagnostic snapshot `sha256:f201918220d6348b776c1dc5b5854a59c3e00cbc8949458c7bc5cb5269ce17ad`; the loader also rejects that ID through both archived cursors and the current pointer. Do not stage the snapshots directory wholesale. If a snapshot is absent or corrupt, continuation fails with 410. Cursor checks bind the request and detect accidental alteration; the unkeyed checksum is not authentication against a malicious client. The current pointer reflects the last successful build; rebuild and republish after changes in current assignments, decisions, or artifacts. A failed rebuild must not be deployed as an update. Previously published snapshots are not revoked automatically.

## Proposed registry adapter, not yet approved for production decisions

For an accepted work only, the canonical registry's **current** `assignment` would contain `ledger_path` and `ledger_sha256`, identifying the current machine-readable assignment ledger. Its `review_decision` would contain exactly:

```json
{
  "format": "literature-registry-export-v1",
  "package": {"path": "en/analysis.json", "sha256": "<sha256>", "revision": "r1", "status": "accepted_partial", "language": "en"},
  "review_path": "review/review.json", "review_sha256": "<sha256>",
  "ledger_path": "assignments.json", "ledger_sha256": "<sha256>",
  "review_decision_path": "review/decision.json",
  "acceptance_path": "acceptance.json", "acceptance_sha256": "<sha256>"
}
```

All paths are inside the site, hashes are lowercase SHA-256 of exact bytes, and the current assignment ledger pointers must match the decision. The review and acceptance files use the existing experimental bridge contract in `tools/literature-en-export/README.md`: they bind the work, exact revision, assigned reviewer, source and package hashes, decision, and independent integrator. This is a proposed mapping for integrator agreement, **not** a declaration that the present Markdown assignments are such a ledger or that any real review is accepted. No decision is inferred from a file, queue state, or hash alone. An author package may retain `not_reviewed`; the separately recorded decisions accept its exact bytes. The operator must verify the authenticity, currentness, revocation state, identities, scientific review, source rights, and immutability during build; the code cannot prove these. The existing bridge requires both RU files and every source as local hash-pinned files.

Tests: `python -m unittest discover -s tools/literature-en-export -v`, `python -m unittest discover -s tools/literature-pipeline -v`, `npm run build`, then `npm run start -- --port 3147`, `node scripts/test-en-http.mjs`, and `npm run knowledge:test -- http://localhost:3147/literature`. Synthetic accepted fixtures are not scientific evidence or real approvals.
