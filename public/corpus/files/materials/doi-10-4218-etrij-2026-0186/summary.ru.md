## 1. Главный вопрос и ответ

По README, работа проверяет, может ли один скрытый участник изменить решение группы LLM-агентов, не взламывая модели и не внедряя инструкции, а только через обычные сообщения в общем обсуждении. Тезис: атакующий сначала строит доверие правильными высказываниями, затем выдаёт ложное утверждение. Коллектив поддаётся не столько аргументу, сколько кажущемуся консенсусу. Авторы называют это социальным доказательством (social proof). Из README видно сочетание трёх частей: поведенческая атака без эксплойта, измерение её эффекта на коллективную точность и тест защиты, которая помечает непроверенные сообщения вместо их удаления. Сравнения с литературой в README нет, поэтому новизну относительно других работ оценить нельзя.

Доказательный статус: исследовательская статья; сам текст не читался, поэтому о качестве доказательств судить нельзя.

## 2. Что проверяли: вопросы и гипотезы

README формулирует не гипотезы, а эксперименты. Из них видны пять вопросов:

1. Снижает ли один скрытый атакующий точность коллективного решения (Exp 2; базовый контроль — Exp 1 без атакующего).
2. Зависит ли эффект от предварительного доверия: инъекция в первом раунде без доверия (Exp 4).
3. Меняет ли структура связей эффект: звезда, где защитники не видят друг друга (Exp 5), кольцо и разреженный граф (`exp_topology`).
4. Работает ли защита — проверяющий модуль Verifier (Exp 6).
5. Может ли адаптивный атакующий обойти ту же защиту, если знает её правила (Exp 8).

Гипотезы о механизме в README сформулированы как интерпретация результата, а не как проверяемое предсказание.

## 3. Агенты, среда и исходные условия

- Семь LLM-агентов в одноранговой сети без оркестратора и без специализации ролей (README, раздел «How it works»).
- Один скрытый атакующий, владеющий 14% мест (1 из 7).
- 40 вымышленных финансовых сценариев (`data/`). По README, каждый содержит два верных сигнала и одну выдумку, а истинное решение можно вывести из заданных данных. Сценарии создала модель o4-mini по промпту из `prompts/`.
- Агенты видят системные сообщения, свои сообщения и сообщения соседей по топологии. Приватные рассуждения и сам вердикт в общий транскрипт не попадают, поэтому агенты оценивают друг друга только по тому, что сказано.
- Основные эксперименты (Exp 1–6) выполнены на GPT-5-mini и повторены пять раз. Межмодельные, топологические и гетерогенные условия, а также Exp 8 — по одному прогону (README, раздел «Reproducing the paper»).
- Точные версии моделей зафиксированы в `moltbook/config.py`.

## 4. Метод и пошаговый пайплайн

1. **Раунд.** Агенты говорят в случайном порядке в общий транскрипт. В основных экспериментах раундов пять, в Exp 3 — семь.
2. **Атакующий.** В Exp 2–7 он управляется моделью, пока строит доверие. Начиная с атакующего раунда он выдаёт фиксированный текст с ложным утверждением, одинаковый для всех моделей и прогонов. В Exp 8 атакующий адаптивный: знает правила верификатора и видит вердикт на собственное предыдущее сообщение. Стадия = min(1 + число отметок, 3). Стадия 1 — утверждение отравленного тезиса. Стадия 2 — выдача его за собственный вывод. Стадия 3 — наводящие вопросы. В приведённом прогоне стадия 3 не достигалась: стадия 1 прошла 101 из 104 сообщений.
3. **Верификатор (Exp 6, 8).** Проверяет каждое сообщение, от защитников и атакующего, по официальной записи. Непроверяемые сообщения не удаляются, а получают предупреждение о происхождении. По README, удаление нарушает обсуждение и порождает вторичные галлюцинации. Верификатор оценивает сообщение изолированно и не видит транскрипта. Авторы подчёркивают, что это сделано намеренно: верификатор, опирающийся на согласие собеседников, воспроизвёл бы ту же уязвимость к консенсусу.
4. **Метрики на финальном раунде.** Точность (Accuracy), SFR (100 − точность; паралич считается провалом), FIR (принятие вердикта атакующего), паралич (откат к вердикту Hold). Процессные метрики: RCR (повтор отравленного словаря при неверном вердикте), OCR (однородность вердиктов), MTTF (раунды до первого провала), DFR (правильный до инъекции, неправильный после). Для верификатора — полнота, доля ложных срабатываний (FPR — доля безобидных сообщений, помеченных как ложные) и точность. Таблица 7 статьи содержит эти значения, но в README их нет.

## 6. Основные результаты (по описанию в README)

- Точность коллектива снижается с 87,5% до 52,5% при одном атакующем. Какие именно условия сравниваются, в README не указано. Вероятно, это Exp 1 и Exp 2, но это требует проверки по статье.
- README определяет метрики FIR (принятие вердикта атакующего) и паралич (откат к Hold), но сами доли по ним не приводит.
- Для адаптивного атакующего (Exp 8) README указывает, что 96,7% его сообщений проходят верификацию. В разделе ограничений тот же README пишет «101 из 104 сообщений» для стадии 1. Но 101/104 ≈ 97,1%, а не 96,7%. Расхождение нужно сверить по статье: возможно, у двух цифр разные знаменатели.
- По README, восстановление точности при защите связано не столько с надёжным распознаванием, сколько с тем, что ограничения верификатора вынуждают атакующего менять риторику.

В заметках корпуса (`input-notes.md`) упомянуты ещё значения: p < 0,0001, почти полное согласие 98,3%, точность 85,8% при маркировке и вдвое больше вызовов модели. В README этих значений нет. Заметки помечены как вторичные, поэтому приписывать эти числа статье без проверки нельзя.

## 7. Что из этого следует и чего не следует

Полезно разделять три слоя.

- **Наблюдаемое (по README):** падение точности коллектива при одном атакующем без технических приёмов; вердикты и тексты сообщений.
- **Заданное авторами:** число агентов, топология, сценарии, скриптованный атакующий, правила верификатора, порядок ходов.
- **Интерпретация (README, раздел «The finding this code supports»):** «society's own deference to apparent consensus does the rest». Это интерпретация механизма. Прямого измерения «уважения к консенсусу» в README нет, и это нужно проверить по статье.

Что из этого следует с осторожностью. Угроза актуальна для многоагентных систем, где агенты доверяют сообщениям друг друга. Проверка отдельного сообщения без контекста ограничивает атаку, но не устраняет её (Exp 8).

Чего из этого не следует. Количественных оценок для реальных финансовых решений нет: сценарии вымышлены. Выводы о масштабировании сговора не делаются, потому что в каждом эксперименте один атакующий.

## 8. Ограничения и воспроизводимость

**Ограничения (по README).**

- Генератор и оценщик частично совпадают: o4-mini создала сценарии и участвует в одном межмодельном сравнении. Её повышенный уровень отказов нельзя отделить от этого совпадения. Независимого валидационного набора не было.
- Один атакующий в каждом эксперименте. Как обнаружение, доля ложных срабатываний и SFR меняются при нескольких атакующих, не проверено.
- Защита в значительной мере обходима (Exp 8).
- Верификатор сам является LLM. Он читает текст атакующего дословно и не укреплён против инъекций, направленных на слой проверки.
- Сценарии чистые: два верных сигнала и одна выдумка. Реальные финансовые обсуждения шумнее и не имеют единственной проверяемой истины.
- Большинство условий выполнено одним прогоном. Пятикратный повтор — только у Exp 1–6 на GPT-5-mini. README называет остальные условия однократными точечными оценками.
- Снимки моделей со временем выходят из обращения. README советует сначала перепрогнать Exp 1, чтобы оценить дрейф модели.

**Воспроизводимость (по README).**

- Код под лицензией MIT. В репозитории есть пакет `moltbook/` (среда и метрики), эксперименты, 40 сценариев в `data/` и промпт генерации сценариев в `prompts/`. Все использованные промпты собраны в `moltbook/prompts.py` с сохранённой опечаткой, поскольку её исправление меняет результаты.
- Для основных экспериментов нужен `OPENAI_API_KEY`. Для межмодельных и гетерогенных условий — `ANTHROPIC_API_KEY` и `GOOGLE_API_KEY`.
- Сырые транскрипты в репозиторий не выложены. По README, их можно получить у авторов или воспроизвести самостоятельно.
- Запуск (по README): смоук-тест `python experiments/exp2_attack.py --limit 3` на трёх сценариях; полное условие — `python experiments/exp6_defense.py`; метрики — `python scripts/analyze_results.py results/...`. Результаты пишутся в `results/` постепенно, поэтому прерванный прогон сохраняет уже выполненную часть.
- Стоимость: README указывает «примерно несколько центов» за смоук-тест на трёх сценариях и даёт оценку вызовов, но не конкретные цены.

## 9. Значение для Лаборатории № 57 и «Верхума»

Ниже три механизма. Все три — **предложения лаборатории**, а не выводы авторов.

1. **Доверие как параметр.** Exp 2 и Exp 4 сравнивают инъекцию с предварительным доверием и без него. **Предложение:** варьировать длительность накопления доверия и измерять, как быстро коллектив исправляет ложный вывод, если появляется независимое доказательство. Предположительно это ложится на теорию активных систем: доверие как параметр связи между элементами системы. Требует проверки и уточнения формализации.
2. **Аргумент против консенсуса.** Верификатор проверяет сообщение без транскрипта. Это модель институционального контроля, где проверка не подвержена давлению большинства. **Предложение:** сравнить изолированную проверку с проверкой в контексте и измерить долю ложных срабатываний у агентов, которые сами не знают истины. В терминах «Верхума» это вопрос о том, как общая память группы влияет на устойчивость к ложным утверждениям.
3. **Социальное доказательство как измеряемое.** RCR и OCR (повтор отравленного словаря и однородность вердиктов) — процессные метрики, которые можно перенести в эксперименты лаборатории по согласованию решений агентов.

Обещать, что стенд на 20 агентах воспроизведёт 87,5% → 52,5%, нельзя. README описывает семь агентов и сценарии с одним атакующим. Масштабирование не проверено.
