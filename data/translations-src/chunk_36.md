## summary
Код и экспериментальные данные к статье Crisis as Catalyst: сценарии распределения юнитов при кризисе и варианты «проблемы вагонетки» (trolley problem), а также анализ и визуализация.
## design
README описывает две экспериментальные задачи: Unit Assignment (назначение юнитов) для межорганизационной кооперации и распределения ресурсов при кризисе, и Trolley Problem (проблема вагонетки) для согласованности моральных выборов. Репозиторий делит исходные данные, результаты и скрипты на модули assignunit и trolley; есть основной и упрощённый режим назначения юнитов и отдельные анализаторы. В видимом описании README не сообщаются полные размер выборки, объём и число повторов; эти параметры следует брать из статьи. Направление исследования — поведенческая согласованность и сравнительный анализ LLM, а не длительный социум.
## tech
Требуются Python 3.8+ и ключи API минимум одного провайдера. В `api.py` настроены провайдеры SiliconFlow, DeepInfra, Azure OpenAI и Google (README); зависимости включают openai, langchain, dotenv, matplotlib, pandas, numpy и seaborn. Есть исходные данные, таблицы и визуализации. README описывает запуск и переменные окружения, но в самой краткой части не фиксирует модели и версии.
## prompts
README не публикует полные промпты времени выполнения (runtime); их следует искать в исходных скриптах. Отдельно фиксировать формулировки критических кризисных сценариев, поскольку они определяют, какие группы взаимодействуют, и варианты моральной «проблемы вагонетки» (trolley), поскольку они составляют экспериментальное воздействие (treatment).
## costs
В README нет проверяемой итоговой стоимости API или подсчёта токенов; стоимость зависит от версий API и числа запусков. Зависимость проекта от нескольких провайдеров не даёт права пересчитывать сумму без данных об использовании (usage data).
## results
README содержит структуру папок data, results и visualization, но не приводит численных находок. Для результатов следует использовать основной журнальный текст и таблицы; карточка не заимствует цифры из пересказа.
## conclusions
Репозиторий является программно-данным артефактом к исследованию кризисного распределения и моральных дилемм, позволяя проверить реализацию анализов. Само наличие кода и данных не подтверждает социальную кооперацию или моральные предпочтения моделей.
## limits
README прямо не раскрывает полный экспериментальный дизайн (experimental design) и численные таблицы; версия данных и конечная точка модели (endpoint) могут меняться. Наличие API-раннера (runner) само по себе не равно воспроизводимости модели; промпты могут повлиять на ответы.

## summary
AutoGen — фреймворк для составления LLM-систем из настраиваемых агентов, инструментов и автоматических диалогов.
## design
README описывает модульную архитектуру: Core API содержит определения агентов, передачу сообщений, событийно-ориентированную локальную и распределённую среду выполнения (runtime), а также поддержку .NET и Python; AgentChat даёт интерфейс, ориентированный на прототипирование, включая двухагентный диалог и групповой чат (group chat); Extensions связывают модельные клиенты (например, OpenAI и Azure OpenAI), исполнение кода и инструменты. AutoGen Studio — графический интерфейс (GUI), AutoGen Bench — набор для оценки. Magentic-One приводится как пример команды, построенной поверх AgentChat и Extensions и способной работать с веб-браузингом, исполнением кода и файлами. Репозиторий разделяет Python-рабочее пространство (workspace) на пакеты autogen-core, autogen-agentchat, autogen-ext и autogen-studio. Документация даёт инструменты для заданных ролей и специализаций, маршрутизации сообщений и кода; состав топологии конфигурируется разработчиком. README (просмотрен 27.10.2026) сообщает, что проект «архивирован и более не поддерживается Microsoft»; для новых проектов он рекомендует Microsoft Agent Framework, а AutoGen характеризует как поддерживаемый сообществом (community-managed). Это актуальный статус; не следует отождествлять его с прежней стадией активно развивающегося исследовательского фреймворка (active research framework).
## prompts
Системные сообщения (system messages) и сообщения ролей определяет создатель приложения; общие README и FAQ дают примеры и назначения, но не единый исследовательский промпт. Для анализа социальности необходимо хранить версию шаблона, правила хода, лимиты инструментов и состояние диалога, поскольку фреймворк позволяет это задавать, но не навязывает.
## costs
Официальный README не публикует единого бюджета API или стоимости токенов. Расход зависит от подключённого провайдера, модели, длины диалога и вызовов инструментов; здесь он не оценивается.
## results
Набор возможностей и границ взят из официальной документации; никакого числа «успешности кооперации» для самого AutoGen карточка не приписывает. Рекомендация перейти на Agent Framework относится к поддержке инструмента, а не к научному сравнению архитектур.
## conclusions
AutoGen полезен как воспроизводимая оркестрационная инфраструктура: он делает видимыми архитектуру сообщений, роли и обмен с инструментами. Для литературы его надо цитировать как программное обеспечение (software), а эмпирические результаты брать из отдельных работ, использующих его.
## limits
Платформа допускает много вариантов архитектуры; результат проекта не задаёт каузального преимущества группового чата (group chat) или конкретной топологии. Текущий репозиторий находится в режиме архива и поддержки сообществом (archive/community maintenance); сохранность, зависимости и различия миграции требуют фиксации коммита (commit) и версии. ## summary
Офлайн-набор Mind Games для тестирования стратегий в Secret Mafia, Codenames, Colonel Blotto и трёхсторонней повторяющейся дилемме; включает эталонных участников.

README говорит, что онлайн-соревнование временно закрыто, при этом офлайн-рабочий процесс (workflow) открыт. Пример использует textarena>=0.7.2, HumanAgent или OpenRouterAgent (пример google/gemini-2.0-flash-lite-001); игровые состояния передаются в `__call__`, агент возвращает текстовое действие. Субмодули для заявок (submissions) нужно инициализировать отдельно; веса моделей не включены в репозиторий (model weights не vendored), есть ссылки на HF и инструкции для скачивания. ## prompts

## costs
Репозиторий не публикует общую смету API; локальные модели требуют GPU, размещённые API (hosted API) — счёт провайдера. Кредиты Modal GPU на $500 в README — предложение облачной инфраструктуры, а не экспериментальная стоимость.
## results

## conclusions

## limits

title_ru: Код оценки к статье «Мультиагентные рассуждения повышают эффективность вычислений: Парето-оптимальное масштабирование на этапе тестирования»

Официальный набор для оценки (evaluation harness) к статье ACL 2026 о качестве и фронте Парето по вычислениям (compute Pareto-front) для CoT, self-consistency, self-refinement, debate и MoA.

README описывает сравнение четырёх методов масштабирования на этапе тестирования (test-time scaling) — self-consistency, self-refinement, multi-agent debate и mixture-of-agents — и их параметризаций при равном бюджете вычислений (matched compute budget). ## tech
Форк EleutherAI lm-evaluation-harness поддерживает пользовательские конвейеры инференса (custom inference pipelines, `lm_eval/models/custom_pipelines_api.py`) для одноагентных и мультиагентных вариантов и обёртку с оценками вычислений (compute estimates) и логированием (logging, `pipeline_evaluations/pipeline_evaluation_wrapper.py`). Промпты и поведение конвейера (pipeline behavior) задаются конфигурацией стратегии — CoT, self-consistency, self-refinement, debate или MoA, а не социальными ролями. Ответы агентов в MoA становятся дополнительным контекстом для последующих слоёв. Полные промпты и конфигурации — в коде и статье.
## costs
Проект моделирует вычислительный расход через оценщик (estimator), однако README не приводит единой денежной сметы API. Сравнение бюджетов вычислений (compute budgets) надо читать как экспериментальную оценку вызовов и вычислений, а не как счёт за API (API invoice).
## results
README сообщает, что при оптимальном масштабировании мультиагентные методы могут быть эффективнее одноагентных; MoA устойчиво выигрывает у debate, self-consistency и self-refinement, а оптимальная MoA часто использует один дополнительный модельный вызов на каждый слой. Более крупная базовая модель без интенсивного test-time compute иногда эффективнее маленькой с масштабированием. ## conclusions
Статья и код дают методологию сравнения качества с равным бюджетом вычислений; нельзя считать «больше агентов» самостоятельной причиной, если сравнение включает различное количество токенов или вызовов.
